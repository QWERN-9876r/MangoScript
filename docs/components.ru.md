# Элементы и компоненты — концепция

[English](components.md) · **Русский**

> Статус: реализованы элементы, компоненты, `state`, `bind:`, `if` / `for` / `switch` в разметке
> (этапы 1–4), рекурсивные компоненты, ранние `return`, `mount()` и веб-компоненты (`@html-tag`);
> `derived`, `effect` и декораторы (`dec`) — ещё нет.
> Принятые решения собраны в конце документа, там же — то, что ещё не решено.

## Цели

1. **Элемент в коде — настоящий DOM-узел.** `<a href="/">…</a>` — это выражение, которое создаёт
   `HTMLAnchorElement`. Виртуального DOM нет.
2. **Компоненты существуют только при компиляции.** В JS нет объектов, классов или функций
   компонентов и нет рантайм-фреймворка: есть только код, который создаёт узлы и обновляет их.
   Компонент — абстракция нулевой стоимости.
3. **Реактивность вычисляет компилятор.** Он видит, какие узлы зависят от какого состояния, и при
   изменении состояния обновляет ровно их. Рантайм-механизмы (прокси, компоненты-функции)
   появляются только там, где без них никак.
4. **Всё проверяется типами:** атрибуты, дети, свойства компонентов, обработчики событий.

## Часть 1. Элементы

### Синтаксис

```go
const name = "на главную страницу"
const link = <a href="/" class="nav">Ссылка {name}</a>     // HTMLAnchorElement
```

Синтаксис как в JSX:

- атрибуты: строка `href="/"`, выражение `href={url}`, без значения `disabled`, spread
  `{...attrs}`;
- дети: текст, выражения в `{...}`, вложенные элементы;
- `<input />` — самозакрывающийся тег, `<>...</>` — фрагмент (`DocumentFragment`);
- `{/* комментарий */}` внутри разметки.

Имена атрибутов — как в HTML, а не как в DOM-свойствах JSX: `class`, а не `className`, `for`, а не
`htmlFor`. В разметке нет конфликта с ключевыми словами, поэтому переименовывать незачем.

Элементы — обычные значения: их можно положить в переменную, вернуть из функции, передать в
`append`. Отдельный механизм ссылок (`ref`) не нужен:

```go
const input = <input placeholder="Имя" />
input.focus()
form.append(input)
```

### Типы

| Литерал               | Тип                                          |
| --------------------- | -------------------------------------------- |
| `<a>`, `<input>`, ... | `HTMLAnchorElement`, `HTMLInputElement`, ... |
| неизвестный тег       | `HTMLElement`                                |
| `<>...</>`            | `DocumentFragment`                           |

Для этого во встроенные типы нужно было добавить DOM: `Node`, `HTMLElement` и самые частые
элементы, `Event` и его варианты, тип `document`. Готово: в Node типы DOM берутся из `lib.dom`
TypeScript, а у компилятора для браузера они написаны вручную.

Что можно передать ребёнком в `{...}`:

- `string` или `number` — становятся текстом;
- `Node` — вставляется как есть;
- `[]T` из таких значений — вставляются по очереди;
- `?T` — `null` не выводит ничего.

`bool` — ошибка: в MangoScript `&&` и так работает только с `bool`, так что идиома JSX
`{ok && <b/>}` невозможна. Вместо неё `{ok ? <b /> : null}` или `{if ok { <b /> }}` (см. ниже).

### Атрибуты и свойства

Компилятор знает DOM и выбирает, как установить значение:

- **Свойство,** если оно есть у элемента: `value`, `checked`, `disabled`, `hidden`, `href`, `id`…
  `class` → `className`, `for` → `htmlFor`.
- **`setAttribute`** — для остальных, в том числе `data-*` и `aria-*`.
- **`style`:** строка — `style.cssText`, объект — по одному свойству.
- **`on*`** — обработчик события, **`bind:*`** — двусторонняя привязка, см. ниже.

Значение атрибута — `string`, `number`, `bool` или `?T` (`null` — атрибута нет). Для известных
свойств тип проверяется точнее: `checked={1}` — ошибка.

### Обработчики событий

```go
<button onClick={count++}>+1</button>                         // код, который выполнится по клику
<button onClick={save(todo)}>Сохранить</button>
<form onSubmit={event.preventDefault(); send()}>...</form>    // несколько операторов через ;
<button onClick={handleClick}>...</button>                     // готовая функция
<button onClick={() => handleClick(1)}>...</button>
```

Правило (как в Vue):

- **Имя, путь `obj.method` или литерал функции** — это сам обработчик.
- **Всё остальное** — операторы, которые выполнятся при событии. Внутри доступна переменная
  `event`.

В отличие от JSX, `onClick={save(todo)}` вызывает `save` по клику, а не при создании элемента.
Классическая ошибка JSX здесь просто невозможна. Правило хорошо ложится на язык: `count++` и
присваивание в MangoScript и так являются операторами, а не выражениями.

`event` типизирован по событию (`onInput` → `InputEvent`), а `event.currentTarget` имеет тип самого
элемента. Поэтому `onInput={title = event.currentTarget.value}` проходит проверку типов без
приведений.

Обработчик выполняется по событию, уже после создания элемента, поэтому может использовать
переменную, которой присваивается элемент (см. «Переменная в собственном инициализаторе» в
спецификации):

```go
const close = <button onClick={close.remove()}>×</button>
```

Атрибут вроде `title={close.title}` читается сразу, поэтому там это ошибка.

### Как компилируется

Элементы вне компонентов статичны: значения из `{...}` вычисляются один раз.

```go
const link = <a href="/" class="nav">Ссылка {name}</a>
```

```js
const link = document.createElement("a");
link.href = "/";
link.className = "nav";
link.append("Ссылка ", name);
```

Если элемент стоит внутри выражения, код его создания выносится перед оператором во временные
переменные. Элемент (и выражения внутри него) создаётся раньше остальной части оператора. В
MangoScript побочные эффекты в выражениях бывают только у вызовов, поэтому это заметно, лишь если
вызовы одного оператора зависят друг от друга. Внутри самой разметки порядок сохраняется.

```go
document.body.append(<p>Привет</p>)
```

```js
const $$p1 = document.createElement("p");
$$p1.append("Привет");
document.body.append($$p1);
```

Выносить нельзя там, где выражение вычисляется не ровно один раз: в ветках `? :`, в правой части
`??`, `&&` и `||`, после `?.`, в условиях `else if` и циклов, в значениях `case` и в полях классов.
Там создание элемента оборачивается в стрелочную функцию, которая тут же вызывается. Стрелочная
функция с разметкой в теле (`items.map(i => <li>{i}</li>)`) получает тело-блок.

Даже без компонентов это заметно упрощает код. Например, `renderItem` из тестового сайта:

```go
func renderItem(todo Todo) HTMLLIElement {
    return <li class={todo.done ? "todo done" : "todo"}>
        <input type="checkbox" checked={todo.done} onChange={toggle(todo.id)} />
        <span>{todo.title}</span>
        <button title="Удалить" onClick={remove(todo.id)}>×</button>
    </li>
}
```

Сейчас та же функция занимает 25 строк вызовов `createElement` и `addEventListener`.

### Лексика

- Пробелы и переводы строк в тексте — по правилам JSX. Строка, где только пробелы, исчезает;
  пробелы с переводом строки по краям текста обрезаются.
- Внутри разметки автоматические `;` не ставятся. Элемент заканчивается на `>` закрывающего тега
  или на `/>`; перевод строки после него ставит `;`, как после любого значения.
- Как и у `{` блока, открывающий тег пишется на той же строке, что `return`: `return <div>`.
  Иначе `return` закончится на переводе строки. Можно также `return (` с переносом.
- `<` в начале выражения однозначен. В языке нет дженериков в `<...>` и приведений `<T>x`, поэтому
  `<` там, где ждут значение, — это всегда элемент, а после значения — сравнение. Но текст внутри
  разметки лексер должен читать по другим правилам. Значит, лексер станет управляемым парсером:
  парсер просит следующий токен в нужном режиме, как это сделано в TypeScript.

## Часть 2. Компоненты

### Объявление и использование

```go
comp Counter(initialValue number) {
    state count = initialValue
    return <button onClick={count++}>Нажато {count} раз</button>
}

document.body.append(<Counter initialValue={0} />)
```

- **Объявление.** `comp Name(параметры) { ... }`. Параметры — свойства компонента, в синтаксисе Go.
- **Использование.** Компонент используется как тег с заглавной буквы. Атрибуты сопоставляются с
  параметрами по имени и проверяются как аргументы функции. Обязательные параметры нельзя
  пропустить, лишний атрибут — ошибка (как лишнее поле в объектном литерале).
- **Необязательные свойства** имеют значение по умолчанию: `comp Button(label string, kind string = "primary")`.
  Значения по умолчанию разрешены только у компонентов: атрибуты именованные, поэтому они здесь
  естественны.
- **Тело выполняется один раз,** при создании (как в Solid). Оно заканчивается `return` разметки.
  Реактивны только разметка, `derived` и `effect`.
- **Ранний `return`** тоже возвращает разметку, например как база рекурсии:
  `if depth > 3 { return <span>…</span> }`. Выбор между `return` делается один раз, при создании;
  внутри выбранной разметки всё обновляется как обычно. Если разметка должна меняться вместе с
  состоянием, её пишут через `{if ...}`. В JS встроенный компонент выходит из своего блока через
  `break` по метке, а компонент-функция — через `return`.
- **Тип `<Counter />`** — тип возвращаемой разметки, здесь `HTMLButtonElement`; при ранних
  `return` — общий тип всех возвращаемых элементов. Использование компонента — такое же
  выражение-элемент, как `<button>`.

### Состояние

| Конструкция                             | Что делает                                                                  |
| --------------------------------------- | --------------------------------------------------------------------------- |
| `state count = 0`, `state items []Todo` | реактивная переменная, как `let`; без значения — нулевое значение типа      |
| `derived double = count * 2`            | вычисляемое значение, только для чтения, как `const`                        |
| `effect { ... }`                        | код, который выполняется после создания и при изменении того, что он читает |

Тип можно указать как у `let`: `state count number = 0`, `derived left number = ...`.

`state`, `derived` и `effect` — ключевые слова только в начале оператора внутри `comp`. В
остальном коде это обычные имена: `let state = load()` по-прежнему можно написать (так же устроены
`static` и `private` в классах).

Изменения отслеживаются по записи в переменную:

- присваивание: `count = 0`, `count += 1`, `count++`;
- изменяющие методы массивов: `todos.push(x)`, `todos.splice(i, 1)`, `todos.sort()`…;
- методы объектов и классов: `list.add(x)`. Что делает метод, компилятор пока не проверяет, поэтому
  изменением считается вызов любого метода, кроме известных читающих (`map`, `filter`, `slice`,
  `toFixed`…);
- запись в поля внутри значения: `todo.done = true`, если `todo` получен из `todos`: через
  `for todo in todos`, `todos.map(todo => ...)` или `const todo = todos[0]`.

Компилятор знает каждое такое место и каждое место, где значение читается, поэтому после записи
вставляет обновление ровно тех узлов, которые от него зависят. Лишнее обновление ничего не
сломает, а пропущенное оставит на странице старое значение. Поэтому анализ осторожный: локальная
переменная с именем состояния даст лишние обновления, но не потеряет нужное.

У `effect` нет отдельного API для очистки. Её делает `defer`: отложенный вызов выполняется перед
повторным запуском эффекта и при удалении компонента.

```go
comp Clock() {
    state now = new Date()
    effect {
        const timer = setInterval(() => { now = new Date() }, 1000)
        defer clearInterval(timer)
    }
    return <time>{now.toLocaleTimeString()}</time>
}
```

`mount()` уже реализован (решение 8): он выполняется, когда разметка уже в документе, а функция,
которую он вернул, — когда разметку убирают `{if}`, `{switch}` или `{for}`.

### Как компилируется

Компонент встраивается в место использования, как макрос. Константные свойства подставляются:

```js
// <Counter>
let $$counter1;
{
  const initialValue = 0;
  let count = initialValue;
  const $$button3 = document.createElement("button");
  $$button3.addEventListener("click", () => {
    count++;
    $$text4.data = count;
  });
  const $$text4 = document.createTextNode(count);
  $$button3.append("Нажато ", $$text4, " раз");
  $$counter1 = $$button3;
}
document.body.append($$counter1);
```

Это весь код: ни функции `Counter`, ни библиотеки. Если зависимостей у состояния несколько или
его меняют в нескольких местах, обновления собираются в одну функцию, которая вызывается после
каждой записи:

```go
comp Counter(initialValue number) {
    state count = initialValue
    derived double = count * 2
    return <p>
        <button onClick={count++}>+1</button>
        {count} × 2 = {double}
    </p>
}
```

```js
let count = 0;
let double = count * 2;
// ...создание узлов...
function $$updateCount2() {
  double = count * 2;
  $$text5.data = count;
  $$text6.data = double;
}
$$button4.addEventListener("click", () => {
  count++;
  $$updateCount2();
});
```

При двух использованиях `<Counter />` получаются два независимых набора переменных: код каждого
использования стоит в своём блоке `{ ... }`.

Встраивание даёт три преимущества:

- **Нет рантайма.** Нет функции компонента, объекта экземпляра и механизма подписок.
- **Константы сворачиваются.** `<Icon name="star" />` превращается только в код для звезды, а
  ветки для других иконок исчезают.
- **Реактивность сквозь компоненты статична.** Если родитель передаёт `count={count}` ребёнку, код
  ребёнка оказывается в том же месте. Поэтому обновление его узлов просто попадает в
  `$$updateCount` родителя, без подписок между компонентами.

Компонент из другого модуля (`export comp`) встраивается так же. Компилятор и сейчас читает
импортируемые `.mango`-модули ради типов, а теперь будет брать оттуда и тело компонента. Вызвать
компонент из JS нельзя: снаружи MangoScript его нет.

### Как устроены обновления

Так это реализовано на этапе 3.

- **Живая разметка** — та, которую компонент создаёт один раз: возвращаемая из тела и элементы,
  объявленные на верхнем уровне тела (`const input = <input />`). Разметка внутри функций и
  выражений (`{items.map(i => <li>{i}</li>)}`) создаётся заново при каждом вычислении, поэтому
  обновлять её на месте не нужно.
- **Текст** (`{count}` типа `string` или `number`) становится текстовым узлом, у которого меняется
  `data`. **Атрибут** обновляется тем же присваиванием, которым был установлен. **Узлы** (`{list}`,
  `{ok ? <b /> : null}`) хранит помощник `$$content`: при обновлении он вычисляет выражение снова
  и заменяет узлы, а те, что остались, переставляет, а не создаёт заново.
- **Функция обновления** — по одной на переменную `state`, с обновлениями всего, что её читает:
  напрямую, через локальные функции компонента или через переменные, которые указывают внутрь
  состояния. Если место записи одно и обновление — один оператор, он пишется прямо в месте
  записи, как в `Counter` выше. Если от переменной ничего не зависит, обновлений нет вообще.
- **Функции тела компонента** (`func add() { todos.push(...) }`) тоже вызывают обновление. Но их
  можно вызвать и в самом теле, когда разметки ещё нет. Поэтому такая функция обновления сначала
  проверяет, создан ли уже компонент: `if (!$$app1) return;`.
- **Код отрисовки обновлений не вызывает.** Это выражения живой разметки, функции компонента,
  которые она вызывает (`{summary()}`), и колбэки, которые они передают (`items.map(...)`). Иначе
  обновление, которое вычисляет `summary()`, запускало бы само себя. Обработчики событий и
  свойства-функции внутри разметки выполняются позже, поэтому обновления в них остаются.
- **Свойство дочернего компонента**, значение которого читает состояние родителя, становится в
  блоке дочернего компонента переменной. Обновление родителя вызывает функцию, которая её меняет
  и обновляет узлы ребёнка:

  ```js
  let $$setValue5;
  {
    let value = count;
    // ...создание узлов...
    $$setValue5 = ($$value) => {
      value = $$value;
      $$text9.data = value;
    };
  }
  function $$updateCount2() {
    $$setValue5(count);
  }
  ```

**Ограничения этапа 3.**

- Изменения внутри функций, которым передали состояние (`sortInPlace(todos)`), не видны. Это задача
  этапа 6; пока после такого вызова нужно присвоить переменную самой себе: `todos = todos`.
- Изменение состояния во время создания разметки (например, свойство-функция, которую дочерний
  компонент вызывает в своём теле) не обновляет уже созданные узлы.
- Узлы из выражения создаются заново целиком: список из `.map()` пересоздаётся при любом
  изменении, а состояние компонентов внутри него сбрасывается. Для изменяемых списков есть
  `{for ...}`, см. «Управляющие конструкции в разметке».

### Когда компонент становится функцией

Встраивать можно не всегда. В двух случаях компилятор делает из компонента функцию:

1. **Компонент рекурсивный** (дерево, вложенные комментарии), напрямую или через другие компоненты.
   Это уже реализовано, см. ниже.
2. **Встраивание добавляет больше 100 лишних строк.** Лишние строки — это суммарный размер всех
   встроенных копий минус размер одной функции и её вызовов. Компонент, который используется один
   раз, встраивается всегда.

Такая функция — деталь компиляции: её нет в экспортах модуля, а имя служебное (`$$Tree`). Свойства
она получает аргументами и возвращает узел и функцию, которая задаёт свойства заново:

```go
comp Tree(item Item, depth number = 0) {
    state open = depth == 0
    return <li>
        <button onClick={open = !open}>{open ? "−" : "+"}</button>
        {item.name}
        {if open {
            <ul>{for child in item.children { <Tree item={child} depth={depth + 1} /> }}</ul>
        }}
    </li>
}
```

```js
function $$Tree(item, depth = 0) {
```

- **Все свойства, кроме `children`,** в функции — источники обновлений: заранее неизвестно, какие
  из них получат состояние вызывающего кода.
- **Вызывающий код** передаёт свойства аргументами, без встраивания, поэтому имена в месте
  использования ничему не мешают. Если значения свойств зависят от его состояния, его обновления
  вызывают возвращённую функцию с новыми значениями.
- **Рекурсия должна заканчиваться.** Если на цикле использований нет ни одного под условием (внутри
  `if`, `for`, `switch`, ветки `?:` или функции), создание компонента никогда не закончится, и это
  ошибка компиляции: `endless recursion: Tree → Tree always creates itself again`.

Подписок по-прежнему нет. Родитель статически знает, какие свойства зависят от его состояния, и
сам вызывает функцию, которая их задаёт, когда это состояние меняется. Потеряно только
сворачивание констант: функция одна для всех мест использования.

### Изменения, которые компилятор не видит: прокси

Статическое отслеживание работает, пока все изменения состояния видны в коде компонента. Прокси
появляются только там, где это не так:

- **Примитивы** (`number`, `string`, `bool`) прокси не нужны никогда: они меняются только
  присваиванием переменной, а его видно.
- **Массив или объект,** который не покидает компонент (в том числе уходит во встроенные дочерние
  компоненты), отслеживается статически.
- **Если значение передаётся в MangoScript-функцию,** компилятор проверяет, меняет ли она его:
  присваивания через параметр, `push` и подобные, передача дальше в меняющие функции. Если не
  меняет, прокси не нужен. Например, `save(todos)` в примере ниже только вызывает
  `JSON.stringify`.
- **Если значение уходит в код, который компилятор не видит** (JS-функции и всё, что имеет тип
  `any`), или в функцию, которая его меняет, состояние оборачивается в прокси. Прокси вызывает
  обновление после любого изменения, в том числе во вложенных объектах (их он оборачивает при
  чтении).

```go
import confetti from "canvas-confetti"          // JS-библиотека: компилятор не знает, что она делает

comp Party() {
    state options = { particleCount: 100, spread: 70 }
    return <button onClick={confetti(options)}>Ура!</button>
}
```

```js
let options = $$reactive({ particleCount: 100, spread: 70 }, $$updateOptions);
```

`$$reactive` — помощник на несколько десятков строк, который попадает в модуль, только если
используется. У прокси есть особенность JS: `options` больше не равен исходному объекту по `==`.
Поэтому компилятор использует прокси только там, где без него обновление потерялось бы.

### Двусторонняя привязка: `bind:`

```go
comp Signup() {
    state name = ""
    state age = 18
    state subscribed = false
    return <form>
        <input bind:value={name} placeholder="Имя" />
        <input type="number" bind:value={age} />
        <label><input type="checkbox" bind:checked={subscribed} /> Подписаться</label>
        <p>Привет, {name == "" ? "незнакомец" : name}!</p>
    </form>
}
```

- **`bind:value`** — для `<input>`, `<textarea>` и `<select>`, тип `string`. Число можно привязать
  к `<input type="number">` и `type="range"`: тогда используется `valueAsNumber`.
- **`bind:checked`** — для `<input>`, тип `bool`.
- **Что можно привязать:** то, чему можно присвоить, — переменную или поле
  (`bind:value={user.name}`, `bind:checked={todo.done}` в списке). Привязать константу, `derived`
  или свойство компонента — ошибка. Вне компонентов `bind:` тоже работает, но только в одну
  сторону: пользователь меняет переменную, а изменения переменной в элементе не видны.

Если `name` меняется не только в поле (например, кнопка «Сбросить» пишет `name = ""`), получается:

```js
$$input4.value = name;
$$input4.addEventListener("input", () => {
  name = $$input4.value;
  $$updateName2();
});
function $$updateName2() {
  if ($$input4.value !== name) $$input4.value = name;
  $$text6.data = name === "" ? "незнакомец" : name;
}
```

Проверка в `$$updateName2` нужна, чтобы не сбрасывать курсор в поле, которое пользователь
редактирует. Само поле обработчик не обновляет: если `name` меняется только в нём, обработчик
обновляет только приветствие, а функции `$$updateName2` нет вовсе.

### Управляющие конструкции в разметке

Внутри `{...}` в разметке можно написать обычные `if`, `for` и `switch`. Элементы в их блоках —
это содержимое:

```go
<div>
    {if todos.length == 0 {
        <p class="empty">Пока пусто</p>
    } else {
        <ul>{for i, todo in todos {
            if !todo.hidden {
                <TodoItem {...todo} position={i + 1} />
            }
        }}</ul>
    }}
</div>
```

- **Синтаксис тот же, что в языке:** `if` / `else if` / `else`, все формы `for` и `switch`.
  Условия проверяются так же, поэтому сужают типы: после `if item != null` в блоке `item` уже не
  `null`. Условие — только `bool`: `if item` для `?T` не пройдёт проверку, нужно `if item != null`.
- **В блоках** — элементы, вложенные `if` / `for` / `switch` и `const`. Другие операторы
  (присваивания, вызовы, `let`, `return`, `break`, `continue`) — ошибка: блок разметки описывает
  содержимое, а не действия. Текст пишется во фрагменте: `{if ok { <>Готово</> }}`.
- **`{выражение}`** по-прежнему работает: `{ok ? <b /> : null}`, `{items.map(...)}`.
- **Spread свойств в компонент** `<Product {...product} />` передаёт поля объекта с именами свойств
  компонента; остальные поля не учитываются. Атрибуты после spread его перекрывают.

**Компиляция.**

- **Если ничего в конструкции не зависит от состояния** (и вне компонентов), получается обычный JS:
  цикл или условие, которые добавляют элементы в родителя.

  ```js
  const $$ul1 = document.createElement("ul");
  for (const [i, product] of products.entries()) {
    if (product != null) {
      // <Product> ...
      $$ul1.append($$product2);
    }
  }
  ```

- **В живой разметке**, если конструкция зависит от состояния, её содержимое хранит помощник
  между пустыми текстовыми узлами-маркерами. Каждый блок — функция, которая создаёт его содержимое
  и возвращает его обновление:
  - `if` / `switch` → `$$branches`: функция выбора возвращает номер ветки. Ветка создаётся заново,
    только когда выбор меняется; иначе обновляется на месте.
  - `for x in xs` → `$$list`: блок для каждого элемента. При обновлении блоки находятся по самому
    элементу массива (объект — по ссылке, строка или число — по значению). Блоки элементов, которые
    остались, обновляются и переставляются, а не создаются заново, поэтому узлы и состояние
    компонентов внутри них сохраняются. Индекс `i` обновляется.
  - Классический `for let i = 0; ...` выполняется заново при каждом обновлении: находить блоки
    там не по чему.
  - `const` в блоке пересчитывается при обновлении, если зависит от состояния.

  ```js
  const [$$for5, $$updateFor5] = $$list(() => todos, (todo, i) => {
    const $$block6 = document.createDocumentFragment();
    // ...создание содержимого...
    return [$$block6, ($$index) => {
      i = $$index;
      $$text8.data = `${i + 1}. ${todo}`;
    }];
  });
  ```

  Обновление блока срабатывает, когда меняется любое состояние, которое блок читает, и обновляет
  все его части. Помощники попадают в модуль, только если используются, так же как
  `$$runDeferred`.

- При удалении ветки или элемента списка выполняются функции, которые вернули `mount()`
  компонентов внутри, включая вложенные блоки. Когда появится `effect`, там же будут выполняться
  его `defer`.

### Дети и события компонентов

```go
comp Card(title string, children Content) {
    return <section class="card">
        <h2>{title}</h2>
        {children}
    </section>
}

<Card title="Профиль">
    <p>Содержимое карточки</p>
</Card>
```

- Параметр `children` типа `Content` получает содержимое между тегами. Его код встраивается туда,
  где стоит `{children}`, — это слоты без рантайма.
- Другие куски разметки передаются обычными свойствами: `<Layout header={<h1>Мой сайт</h1>} />`.
- События наружу — свойства-функции, с тем же правилом обработчиков, что у `on*` в элементах:

```go
comp TodoItem(todo Todo, onToggle func(), onRemove func()) {
    return <li class={todo.done ? "todo done" : "todo"}>
        <input type="checkbox" checked={todo.done} onChange={onToggle} />
        <span>{todo.title}</span>
        <button title="Удалить" onClick={onRemove}>×</button>
    </li>
}

<TodoItem todo={todo} onToggle={todo.done = !todo.done} onRemove={remove(todo.id)} />
```

Свойства только для чтения: присвоить параметру внутри компонента нельзя. Чтобы изменить
состояние родителя, его передают через свойство-функцию, как `onToggle` выше.

### Декораторы

> Ещё не реализовано: это согласованный дизайн.

Декоратор добавляет компоненту логику: своё состояние, функции, `mount()` и обёртку вокруг того,
что вернул компонент. Компоненты — это не только вёрстка, и общую для многих из них логику (загрузку
при появлении на экране, страницу 404, аналитику, проверку доступа) пишут один раз, в декораторе.
Как и компонент, декоратор существует только при компиляции: его код встраивается в каждый
компонент, к которому он применён.

```go
// Сообщает, появился ли компонент в области видимости (с запасом margin)
dec visible(margin string = "0px") {
    public state shown = false
    let node ?Element = null

    public func show() {
        shown = true
    }

    mount() {
        const observer = new IntersectionObserver(entries => {
            if entries.some(entry => entry.isIntersecting) {
                show()
                observer.disconnect()
            }
        }, { rootMargin: margin })
        if node != null {
            observer.observe(node)
        }
        return () => observer.disconnect()
    }

    // Ничего не меняет, только запоминает узел для mount
    return (content Element) => {
        node = content
        return content
    }
}

@visible("300px")
comp Playground() {
    state source = ""

    func open(code string) {
        source = code
        @visible.show()
    }

    return <section>
        {if get(@visible.shown) {
            <Editor source={source} />
        }}
    </section>
}
```

- **Объявление.** `dec имя(параметры) { ... }`. `dec` — ключевое слово только в начале объявления
  на верхнем уровне модуля, в остальных местах это обычное имя. Параметры записываются как у
  функций, но в конце у них могут быть значения по умолчанию: `margin string = "0px"`.
  `export dec` экспортирует декоратор, и в другом модуле он встраивается так же, как компонент.
- **В теле** могут быть `state`, `const`, `let`, функции, `mount() { ... }` и в конце — `return`
  обёртки. Всё это необязательно: декоратор без обёртки только добавляет состояние и логику.
- **Применение.** `@visible("300px")` перед `comp`. Аргументы позиционные, как при вызове функции;
  без аргументов скобки можно опустить: `@notFound`. Аргументы вычисляются для каждого экземпляра в
  области параметров компонента, поэтому `@card(product.price)` работает у
  `comp ProductCard(product Product)`. Когда параметр меняется, декоратор получает новое значение,
  как свойство дочернего компонента.
- **Публичные члены** — `public state`, `public const` и `public func` — видны компоненту:
  - чтение — `get(@visible.shown)`; в разметке оно обновляется так же, как чтение собственного
    состояния компонента;
  - вызов — `@visible.show()`;
  - запись снаружи — ошибка:
    `"shown" of @visible is read-only outside it; change it with one of its public functions, e.g. @visible.show()`.
    Как и со свойствами компонентов, декоратор сам следит за согласованностью своего состояния;
  - `get` особый, только когда его аргумент начинается с `@`, поэтому своя функция программы
    `get(url)` продолжает работать. `visible.shown` без `@` и `@visible.shown` вне `get` — ошибки
    с подсказкой `get(@visible.shown)`;
  - `public let` нет: значение, которое меняется и читается снаружи, — это `state`, а то, которое не
    меняется, — `const`.

  Без `public` члены видны только внутри декоратора, и там к ним обращаются просто по имени:
  `shown`, `show()`.

- **Декоратор не видит компонент:** ни его состояние, ни его параметры, кроме как через аргументы.
  Поэтому один декоратор подходит любому компоненту.
- **Обёртка** `return (content T) => ...` получает то, что вернул компонент, и то, что она вернёт,
  компонент в итоге и возвращает. Тип параметра пишется явно: тело декоратора проверяется один раз,
  само по себе, а не заново при каждом применении. Тип ещё и ограничивает, к чему декоратор можно
  применить: с `(form HTMLFormElement) => ...` — только к компонентам, которые возвращают форму.
  Тип `<Playground />` — результат самой внешней обёртки. `return` должен возвращать литерал
  функции.
- **Обёртка вызывается один раз,** при создании, как тело компонента. Чтобы показанное менялось
  потом, разметка обёртки читает состояние декоратора:

  ```go
  dec notFound() {
      state missing = false

      public func show() {
          missing = true
      }

      return (page Element) => <div class="page">{missing ? <NotFoundPage /> : page}</div>
  }
  ```

**Несколько декораторов,** `@a @b comp X`:

- тела выполняются сверху вниз: `a`, `b`, затем тело компонента;
- обёртки применяются снизу вверх: результат компонента получает `b`, а результат `b` — `a`;
- `mount()` выполняется изнутри наружу: компонент, `b`, `a`; очистка — в обратном порядке;
- повторное применение одного декоратора — ошибка: `@a.x` стало бы неоднозначным;
- `@html-tag` должен стоять первым: элемент строится из итогового результата.

**Зависимости.** Декоратор видит публичные члены другого, только если назвал его в `needs`:

```go
dec cart() {
    public state count = 0

    public func add() {
        count++
    }
}

dec cartBadge() needs cart {
    return (content Element) => <div class="with-badge">
        {content}
        <span class="badge">{get(@cart.count)}</span>
    </div>
}

@cart
@cartBadge
comp ProductCard(product Product) {
    return <article>
        <h2>{product.name}</h2>
        <button onClick={@cart.add()}>В корзину</button>
    </article>
}
```

Тело `cartBadge` может читать состояние `cart` при создании, поэтому `cart` уже должен существовать.
`@cartBadge` без `@cart` или с `@cart` ниже — ошибка компиляции:
`@cartBadge needs @cart above it: @cart @cartBadge comp ...`. Несколько перечисляются через
запятую: `dec checkout() needs cart, auth { ... }`.

**Компиляция.** Декоратор встраивается, как компонент: его тело попадает в блок каждого экземпляра
перед телом компонента, а его имена переименовываются. `get(@visible.shown)` становится чтением
этой переменной, `@visible.show()` — вызовом этой функции, а обновления состояния декоратора
включают разметку компонента, которая его читает. Разметка обёртки создаётся вокруг результата
компонента. Объектов декораторов и рантайма нет.

**Позже:** встроенный декоратор высшего порядка будет объединять несколько декораторов в один.
Объявлять свои декораторы высшего порядка программа не может.

### Пример: тестовый сайт на компонентах

Тот же список задач, что сейчас в `site/src/app.mango` (около 90 строк ручной работы с DOM):

```go
import { Todo, parseTitle } from "./todos.mango"
import { load, save } from "./storage.mango"

const FILTERS = [
    { id: "all", label: "Все" },
    { id: "active", label: "Активные" },
    { id: "done", label: "Готовые" },
]

comp TodoApp() {
    const saved, loadError = load()
    state todos = saved
    state title = ""
    state message = loadError?.message ?? ""
    state filter = "all"

    derived visible = todos.filter(todo => matches(todo, filter))
    derived left = todos.filter(todo => !todo.done).length

    // Список сохраняется при каждом изменении. save его только читает, поэтому прокси не нужен.
    effect {
        save(todos)
    }

    func add() {
        const text, err = parseTitle(title)
        if err != null {
            message = err.message
            return
        }
        todos.push({ id: Date.now(), title: text, done: false })
        title = ""
        message = ""
    }

    return <main>
        <form onSubmit={event.preventDefault(); add()}>
            <input bind:value={title} placeholder="Что сделать?" />
            <button>Добавить</button>
        </form>
        {if message != "" {
            <p class="message">{message}</p>
        }}
        <nav>
            {for f in FILTERS {
                <button class={f.id == filter ? "active" : ""} onClick={filter = f.id}>{f.label}</button>
            }}
        </nav>
        <ul>
            {for todo in visible {
                <TodoItem
                    todo={todo}
                    onToggle={todo.done = !todo.done}
                    onRemove={todos = todos.filter(t => t.id != todo.id)}
                />
            }}
        </ul>
        <footer>Осталось: {left}</footer>
    </main>
}

func matches(todo Todo, filter string) bool {
    switch filter {
    case "active":
        return !todo.done
    case "done":
        return todo.done
    default:
        return true
    }
}

document.body.append(<TodoApp />)
```

В JS из этого получится код создания узлов, по одной функции обновления на состояние и `$$list`
для списка задач. Прокси и компонентов-функций здесь нет. `TodoItem` встроен в тело `for`: код
одной строки списка написан там один раз, и лишних строк не появляется.

| Компонент в рантайме          | функция            | функция                         | нет: код встраивается (функция — только если большой или рекурсивный) |

| Общая логика компонентов      | хуки, HOC          | actions (Svelte), примитивы     | декораторы `dec`, встраиваются                                        |

## Что придётся сделать в компиляторе

- **Лексер:** режим разметки (текст, атрибуты), управляемый парсером.
- **Парсер:**
  - узлы `ElementExpression`, `Attribute`, `TextChild`, `ExpressionChild`;
  - `if` / `for` / `switch` в разметке;
  - объявление `ComponentDeclaration` с `state`, `derived` и `effect`.
- **Типы:** DOM во встроенных; атрибуты, `bind:` и свойства компонентов; правила `state`,
  `derived`, `effect`.
- **Анализ:**
  - зависимости разметки, `derived` и `effect` от состояния;
  - места записи;
  - меняет ли функция свой параметр;
  - рекурсия компонентов;
  - размер встраивания.
- **Генерация:**
  - создание узлов;
  - встраивание компонентов с переименованием и компоненты-функции;
  - функции обновления;
  - `if` / `for` / `switch` в разметке;
  - помощники `$$list` и `$$reactive`.

## Решения

1. **Состояние объявляется ключевыми словами:** `state count = 0`, `derived double = count * 2`,
   `effect { ... }`.
2. **Рекурсивные компоненты:** в первой версии — ошибка компиляции, затем — компиляция в функцию.
   Сейчас они компилируются в функции.
3. **Прокси — только там, где без них никак:** для массивов и объектов, которые уходят в код, не
   видимый компилятору, или в функции, которые их меняют.
4. **Двусторонняя привязка — `bind:value` и `bind:checked`.**
5. **Общее состояние нескольких компонентов** добавим позже; пока его передают через свойства.
6. **Порог встраивания:** если встраивание добавляет больше 100 лишних строк кода, компонент
   становится функцией.
7. **Условия и циклы в разметке — обычные `if`, `for` и `switch` внутри `{...}`**, без отдельного
   синтаксиса вроде `@if`: `<div>{for product in products { <Product {...product} /> }}</div>`.
8. **Монтирование — `mount() { ... }` в теле компонента.** Выполняется, только когда разметка
   компонента в документе: это проверяется в микрозадаче после создания, а разметку, которой в
   документе ещё нет, ждёт `MutationObserver` — он следит, только пока какая-то разметка ждёт.
   Первый узел запоминается сразу после создания разметки: фрагмент после вставки пустеет. Функция,
   которую вернул `mount`, выполняется, когда разметку убирают `{if}`, `{switch}` или `{for}`. Для
   этого блоки создаются с «владельцем»: он собирает очистку компонентов блока и вложенных блоков.
   Владелец текущего блока общий для модулей страницы (`Symbol.for("mangoscript.owner")`), потому
   что в блоке одного модуля могут оказаться компоненты другого. Удаление разметки собственным
   кодом программы не отслеживается: для этого наблюдатель за всем документом работал бы всё время,
   а очистка вызывалась бы асинхронно.
9. **Веб-компоненты — `@html-tag comp ...`.** Тег берётся из имени компонента в kebab-case или из
   декоратора, `@html-tag("app-card")`; имя без дефиса — ошибка компиляции, а не догадка. Такой
   компонент компилируется в функцию, как рекурсивный, а класс пользовательского элемента вызывает
   её в `connectedCallback` и рисует в shadow root. Атрибуты преобразуются по типу свойства (строка,
   `Number()`, наличие для bool); массивы, объекты и функции — только JS-свойства. Отключение
   удаляет разметку в микрозадаче, если элемент к тому времени не вернули, поэтому перемещение
   сохраняет состояние. Элемент регистрируется в конце модуля, чтобы он не запустился раньше, чем у
   используемых им имён появятся значения.
10. **Общая логика компонентов — декораторы, `dec имя(...) { ... }`,** применяются при компиляции
    (см. «Декораторы»). Они не для собственного состояния компонента, а для логики, которую к нему
    добавляют. Аргументы позиционные и вычисляются в области параметров компонента. Публичные
    члены — `public state`, `public const` и `public func`, без `public let`; снаружи их читают
    через `get(@имя.член)` и вызывают как `@имя.f()`, а запись снаружи — ошибка. Тип параметра
    обёртки пишется явно. Один декоратор видит другой только через `needs`, и нужный ему должен
    быть применён выше. Повторное применение декоратора — ошибка. Объявлять декораторы высшего
    порядка программа не может: декораторы будет объединять только встроенный.

## Ещё не решено

1. **Сообщать ли, где компилятор отступил от встраивания.** Компоненты-функции и прокси — неявные
   решения, которые влияют на выходной код. Предлагаю флаг `mango build --explain`, который их
   перечисляет: «`Card` стал функцией: 140 лишних строк», «`options` обёрнут в прокси: передаётся в
   `confetti`».
2. **Порог в 100 строк — константа или настройка.** Предлагаю пока константу, а настройку
   (`--inline-limit`) добавить, когда появится реальная потребность.
3. **Явный ключ для `for`.** Сейчас блоки списка находятся по самому элементу. Если массив
   заменяют новыми объектами с теми же данными (например, загрузили заново с сервера), все блоки
   создаются заново. Если это станет проблемой, можно добавить ключ, например
   `for todo in todos key todo.id`.
4. **`derived` из нескольких операторов.** Сейчас `derived x = выражение`. Можно добавить блочную
   форму `derived total number { ... return sum }`. Предлагаю в первой версии только выражение:
   сложную логику можно вынести в функцию.
5. **Объединение декораторов.** Не решены синтаксис встроенного декоратора высшего порядка и то,
   как он работает с остальным: читаются ли публичные члены объединённых декораторов как
   `get(@card.count)` или через имя объединения, удовлетворяет ли объединение, в котором есть
   `cart`, условию `needs cart`, и считается ли `@cart` рядом с объединением, в котором он есть,
   повторным применением.
6. **Компонент, который возвращает `null` для обёртки.** Страницу 404 можно было бы сделать
   обёрткой `(page ?Element) => ...`, которая показывает её, когда компонент вернул `null`. Сейчас
   компонент возвращает только разметку, а выбор между `return` делается один раз, при создании;
   реактивный способ — состояние декоратора, как в `notFound` выше.
